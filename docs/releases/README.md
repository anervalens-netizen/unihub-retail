# Release narratives — derived views only

Markdown in this directory is **not** production release authority.

The release identity chain is machine-readable:

1. `RELEASE_MANIFEST.json` is the signed exact-SHA candidate identity generated by CI.
2. D2 `release.env` is the exact deployment/promotion-state record and carries the deployed SHA, migration head, artifact/SBOM digests, deployment timestamp and predecessor/rollback identity.
3. D3 annotated tags use `production/retail-release-<full 40-character source SHA>` as immutable promotion-history evidence.

A human-readable production view must be generated from an exact verified D2 promotion record rather than edited by hand:

```bash
python3 scripts/render_production_release_notes.py /exact/path/to/release.env
```

The renderer is fail-closed and accepts only a complete `PROMOTION_SCHEMA_VERSION=1`, `STATE=deployed` record with internally consistent SHA/release/predecessor/rollback identities, canonical timestamps and digests. It prints Markdown to stdout; it does not discover a release, write a repository pointer or declare `current`/`latest` state.

Selecting which deployment record represents the operational state is outside this narrative layer. Do not infer production state from filename order, semantic-version order, Git commit recency, or the newest tag alone.

## Historical notes

The files `v2.0.0.md`, `v2.0.1.md` and `v2.1.0.md` preserve what was documented at those historical releases. Their dates, SHA references, deployment evidence and version-policy statements are historical evidence only. They must not be interpreted as the current production identity or as a replacement for the signed candidate/promotion records above.
